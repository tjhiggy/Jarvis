# Jarvis v0.5.0 Shipboard Broadcasts release package

**Status:** Prepared for independent review. This is not a deployed release,
tag, or GitHub publication.

## What changes

Jarvis v0.5.0 adds server-scoped, durable delivery control for RSS, approved
proactive posts, recaps, event reminders, and birthday mentions. It keeps
public channel broadcasts separate from personally targeted notifications:
only event reminders and birthdays have durable crew opt-in, and Jarvis sends
no unsolicited direct messages.

Each category has a durable policy containing state, configured channel, IANA
timezone, optional quiet-hour bounds, minimum interval, digest mode, and safe
update metadata. The environment destination allowlist remains authoritative.
Startup creates missing configured policies without overwriting existing
operator choices. RSS defaults to enabled UTC digest delivery with no interval;
proactive defaults to enabled UTC, 23:00-08:00 quiet hours, and a six-hour
interval; recap, event-reminder, and birthday policies default to enabled in
the configured recap timezone without quiet hours or cadence.

The database migration is additive: `broadcast_schema_migrations`,
`broadcast_policies`, `member_notification_preferences`, and
`broadcast_delivery_runs`. Generic cleanup deletes only old completed delivery
runs in bounded batches. It never expires policy or preference records.

## Operator rollout and smoke checklist

Complete this in a non-sensitive staging MuthaShip after the reviewed revision
is deployed and command registration is explicitly authorized.

- [ ] Back up the cleanly stopped production SQLite database and its WAL state.
- [ ] Confirm `ALLOWED_CHANNEL_IDS` contains every non-RSS broadcast
      destination; confirm RSS channel and RSS host allowlist are intentional.
- [ ] Set `ENGAGEMENT_PROACTIVE_CATALOG_PATH` only to a reviewed local JSON
      file, restart, and confirm invalid catalog text prevents startup.
- [ ] Run `/status` and verify the explicit v0.5.0 version and merge SHA.
- [ ] Run `/notifications status`, enable and disable event reminders and
      birthdays, and confirm RSS is explained as a public channel broadcast.
- [ ] Use RSS preview, save an approved feed, and confirm baseline creation
      posts no history. Trigger one fresh entry, simulate a Discord failure, and
      confirm one later leased retry rather than a duplicate.
- [ ] Use proactive preview, verify an inactive/out-of-window prompt does not
      post, then verify an approved active prompt respects quiet hours and cadence.
- [ ] Pause and resume one category through the local Command Deck. Exercise
      global engagement pause, then confirm both controls suppress at the final
      pre-post check.
- [ ] Restart one process while a delivery is pending and confirm completed
      RSS, proactive, recap, event-reminder, and birthday work is not duplicated.
- [ ] Verify recap, event-reminder, and birthday suppression. Confirm an event
      reminder needs RSVP and notification opt-in, and a birthday needs its record
      and notification opt-in.
- [ ] Inspect the Command Deck at desktop and mobile widths: cards must show
      friendly destinations, quiet hours, cadence, eligibility, health, and 7/30
      day aggregate metrics without raw IDs or content.
- [ ] Confirm a failed delivery reports a bounded health/error category and
      that metrics contain only event, category, UTC day, count, and duration.
- [ ] Rehearse rollback on a disposable database copy before production change.

## Disposable migration and rollback rehearsal

1. Stop the production process cleanly. Make a timestamped copy of the
   production database, and retain it as read-only evidence. Never run a new
   binary against the production path during rehearsal.
2. Copy that backup to a disposable directory. Set `DATABASE_PATH` for the
   rehearsal process to the disposable copy, start the built v0.5.0
   application, and verify the four broadcast tables and migration row exist.
   Verify missing configured policy rows receive their documented defaults.
3. Stop the rehearsal process cleanly. Replace the disposable database with the
   backup copy, start the prior approved application against the disposable
   path, and verify it opens successfully. The prior release ignores additive
   broadcast tables, so no destructive downgrade migration is needed.
4. Record only date/time, approved backup location, version, result, and
   operator. Keep production data, IDs, content, and credentials out of the
   record. A failed rehearsal blocks deployment.

## Release gates and publication order

Before publishing, run `npm test`, `npm run build`, `npm run lint`,
`npm run format:check`, `npm run docs:check`, `npm audit --audit-level=high`,
and `git diff --check`. An independent reviewer must clear destination bypass,
mentions, secrets, content logging, lease races, duplicates, shutdown races,
retention loss, and misleading success claims. Then: merge the approved PR,
deploy that merge, register commands, complete the checklist, tag `v0.5.0`,
publish GitHub release notes, and close verified work. Do not reverse this
order just because a tag button looks temptingly shiny.

## Rollback

Pause the affected category and global engagement if necessary. Stop Jarvis,
back up the stopped current database, deploy the prior approved revision, and
restore the approved known-good backup only when state rollback is required.
Register commands if definitions differ, start one process, then verify
`/status`, broadcast health, and one non-sensitive configured feature. Preserve
the pre-rollback database and content-free incident evidence for recovery.
